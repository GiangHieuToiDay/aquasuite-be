UC-24 / CREDIT FLOW — CURRENT IMPLEMENTATION AND DEPENDENT UC HANDOFF

Customer credit profile is logical data on customers, not a separate debt-account table. When CRM creates a Customer, credit_limit is 0 and credit_term_days is null, so the Customer is not eligible for credit sales. A Sales Staff member creating a POS credit order first requests Quick Credit Approval when the Customer has no usable limit. The Store Owner enters the credentials of an existing LOCAL IAM account on the same POS popup. IAM verifies that password and active SHOP_OWNER role, then creates an opaque Redis approval grant valid for two minutes and usable once only. The grant is bound to the initiating Sales Staff, Customer, approved limit, and approved payment term. CRM consumes the grant through PATCH /api/v1/crm/customers/{customerId}/credit-profile, updates customers.credit_limit and customers.credit_term_days, and emits an audit event recording both requester and approving Store Owner. Sales Staff is never replaced by the Owner session. A Google-only Owner cannot use this v1 approval flow because it has no LOCAL password.

UC-21 BACKEND IS ALREADY IMPLEMENTED IN THIS CHECKOUT. SalesOrderServiceImpl now calls finance.api.CreditControlApi.authorize(...) only for PaymentMethod.CREDIT, after calculating the final order total but before inventory reservation and Order persistence. The Finance final authorization uses the Customer profile and derived exposure to reject BLOCKED, blacklisted, overdue, or over-limit credit sales. A failed decision prevents reserveStock and save(Order); an approved decision permits the normal PROCESSING / UNPAID Order flow. UC-21 no longer sets orders.due_date to order creation date plus 30 days; Order dueDate is null because payment due date belongs to an issued invoice. The UC-21 frontend/POS still needs to invoke the IAM grant endpoint and CRM profile endpoint before it calls the existing Order-create endpoint for a first-time or over-limit credit customer.

UC-24 derives, rather than stores, customer amounts from active Orders, ISSUED invoices, and VERIFIED receipt transactions. It now exposes unbilledCommitment for the confirmed Order value not yet invoiced, issuedInvoiceReceivable for invoice amounts not yet paid, unallocatedAdvanceAmount for an order-linked verified receipt not yet allocated to an invoice, and outstandingBalance as net credit exposure. An Order in PROCESSING holds exposure. A CANCELLED Order is excluded. UC-26 PENDING_CANCEL is a modification-request state, not an Order cancellation, so it must continue to hold exposure until tax adjustment/cancellation and any refund are complete.

The V6 migration adds sales_invoices.credit_term_days and sales_invoices.due_date. The agreed rule is dueDate = invoice.issueDate + creditTermDays effective when that Invoice becomes ISSUED. Existing Finance read code uses the snapshot when populated and retains a legacy fallback for old invoices. The owner of the Invoice issuance UC must set both snapshot fields atomically when it changes Invoice status to ISSUED. Later Customer profile changes must apply only to future invoices and must never recalculate an existing Invoice due date. Fulfillment must issue an invoice only for the delivered/accepted batch in a staged delivery flow.
