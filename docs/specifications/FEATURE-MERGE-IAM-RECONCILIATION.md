# Feature Specification — IAM Merge Reconciliation

## Metadata and Governance

- **Feature ID**: `FEATURE-MERGE-IAM-RECONCILIATION`
- **Feature Name**: Quarantine legacy IAM recovery and implement UUID in-memory recovery
- **Version**: `0.2.0`
- **Owner / Author**: AquaSuite Backend Team
- **Owning Module**: `iam`
- **Repository Scope**: `BE (aquasuite-be)`
- **Target Package**: `com.aquasuite.ims.module.iam`
- **Database Baseline**: `PostgreSQL` — empty target receives Inventory baseline V2
- **Spec Review Status**: `APPROVED`
- **Spec Review Approver**: `Project Owner`
- **Spec Review Evidence**: Explicit owner approval recorded on 2026-10-20
- **Risk Level**: `HIGH`

## 1. Business Context and Objectives

### Problem Statement

The merged branches load two incompatible JPA models for `public.users`: a
legacy Long-ID password-recovery model and the canonical UUID/RBAC IAM model.
The legacy source must remain intact for its owner, but cannot participate in
runtime because it conflicts with the Flyway V1 schema and UUID authentication.

### Business Goals & Scope

- Load only the canonical UUID/RBAC user entity and repository at runtime.
- Preserve the existing password HTTP routes and `ApiResponse` envelope.
- Implement password recovery on the UUID model without persistence for recovery
  state, and create the missing Inventory baseline schema using UUID audit IDs.
- Keep recovery state in application memory and preserve legacy source without
  logic modifications.

### Out of Scope

- Recovery OTP database storage, a Long-to-UUID data conversion, or support for
  an existing populated Inventory schema.
- Redis/distributed recovery state or multi-instance recovery support.
- JWT or Redis session redesign, endpoint changes, and edits to legacy recovery
  business logic.

## 2. Actors, Permissions, and Security Model

| Actor | Identity Source | Authorized Operations | Required Permission |
|---|---|---|---|
| Account owner | Identifier plus OTP | Request and reset password | Valid recovery challenge |
| Active user | UUID subject in JWT | Change own password | Authenticated self-service |
| IAM runtime | Spring context | Load canonical IAM only | Internal |

### Data Protection and Sensitive Fields

- Raw passwords and OTP values must never be persisted or logged.
- The in-memory store retains only a password-encoder OTP hash, UUID user ID,
  expiry, attempt/rate-limit state, and non-sensitive channel metadata.
- No response exposes recovery-store internals or account-existence details
  beyond the currently approved HTTP contract.

## 3. Detailed Business Rules and Logic

1. The canonical UUID `User` entity and repository are the only IAM persistence
   model loaded at runtime.
2. Legacy recovery packages remain source-preserved but are excluded from Spring
   component, JPA entity, and JPA repository scanning.
3. `POST /forgot` creates or replaces an in-memory challenge for a normalized
   identifier/channel. It expires after ten minutes.
4. OTP is generated by `SecureRandom`, stored only as a hash, and is single use.
   A successful reset removes it.
5. Each challenge accepts at most five failed verifications and five send
   requests in its in-memory day window.
6. `POST /change` obtains the caller UUID from JWT/security context; production
   code has no mock Long-ID fallback.
7. Restart clears every challenge and rate-limit record. Multiple instances do
   not share challenges; these endpoints require a single active instance.

### Recovery Challenge Lifecycle

| From State | Action | To State | Invariant |
|---|---|---|---|
| Absent | Valid recovery request | Active | Hash and expiry exist only in memory |
| Active | Valid OTP and new password | Consumed | Password changes; challenge is removed |
| Active | Expiry, five invalid attempts, or restart | Absent | OTP is unusable |

## 4. Data Model and Schema Impact

### Owned Runtime State

- `PasswordRecoveryChallenge` is an internal in-memory value object: UUID
  `userId`, OTP hash, expiry, attempts, send-window state, and a key.
- `InMemoryPasswordRecoveryStore` is an internal singleton with a bounded,
  expiry-cleaned `ConcurrentHashMap`; it is not a JPA entity or distributed cache.

### Cross-Module References

No cross-module JPA association is introduced. The flow references only the
IAM-owned UUID user model.

### Database Migration

The confirmed target is an empty database. `V2__create_inventory_baseline.sql`
creates the inventory schema reflected by the existing entities:

- `inventories`, `stock_movements`, `stock_counts`, `stock_count_items`,
  `suppliers`, and `supplier_products`;
- UUID primary keys and scalar UUID references for SKU/product and IAM audit
  identifiers; no cross-module JPA association is introduced;
- `stock_movements.created_by`, `stock_counts.counted_by`, and
  `stock_counts.approved_by` as nullable UUID columns;
- indexes and PostgreSQL check constraints that mirror current enum and quantity
  invariants.

The migration is a baseline for an empty database. It must not use `IF NOT
EXISTS`, drop/alter existing tables, or attempt to transform legacy Long audit
values.

## 5. API and Contract Specifications

### 5.1 External HTTP Endpoints

The following endpoints and their JSON request/response contracts remain
unchanged and use `ApiResponse<T>`:

- `POST /api/v1/iam/password/change`
- `POST /api/v1/iam/password/forgot`
- `POST /api/v1/iam/password/reset`

Bean-validation errors continue to use the centralized `FieldErrorDetail`
format. The implementation returns no OTP, password hash, or recovery state.

## 6. Concurrency, Transactions, and Failure Scenarios

### Concurrency Controls

- Updates for one challenge key are atomic: concurrent reset attempts yield one
  successful consume.
- The bounded store removes expired entries without retaining a raw OTP.

### Transaction Boundaries

- Canonical password-hash updates use the IAM database transaction.
- Store mutation is process-local and cannot be atomic with PostgreSQL; a
  database failure leaves the challenge usable until expiry or retry.

### Failure and Recovery

- Restart or deployment invalidates challenges by design; the user requests a
  new OTP.
- Multiple instances are unsupported for this flow until a separately approved
  shared-store design exists.
- OTP delivery failure never logs raw OTP; handling removes or preserves a
  challenge only through an explicit service-level policy.

## 7. Acceptance Criteria

- [ ] **AC-01**: Spring loads no legacy IAM entity, repository, or recovery
  service bean and has no duplicate `users` mapping/repository bean name.
- [ ] **AC-02**: An authenticated UUID user changes only their own password;
  there is no production mock identity.
- [ ] **AC-03**: Recovery stores a hash-only OTP and permits one valid reset
  before expiry.
- [ ] **AC-04**: Expiry, replay, five invalid attempts, and restart invalidate
  the challenge.
- [ ] **AC-05**: Existing password endpoints keep their HTTP/JSON envelope.
- [ ] **AC-06**: No database migration/schema change and no legacy recovery
  business-logic edit occurs, except V2 creates the documented Inventory
  baseline in an empty database with UUID audit columns.
