# UC-22.7 – Process Warranty Ticket

> English version of `UC-22.7-use-case-specification.vi.md` (the Vietnamese version is the source; keep both in sync). Written to match the **current code**. Messages are quoted exactly as they appear on the screen (Vietnamese).
> The team removed the Technical Staff role (24/11/2026): the Shop Owner is the only person who handles warranty tickets; the system does not assign staff and does not create technical jobs.

|  |  |  |  |
| :-: | :-- | :-: | :-- |
| Primary Actors | Shop Owner | Secondary Actors | None |
| Created By | Pham Van Nam | Created Date | 24/11/2026 |
| Description | As the Shop Owner, I want to handle a customer's warranty ticket until it reaches a final result (accept it for processing and then complete it with a result, or reject it with a reason), so that the customer receives a clear answer and every handling step is traceable. |  |  |
| Preconditions | 1. The user is logged in with the Shop Owner role.<br>2. The warranty ticket has been submitted by a customer and the Shop Owner has found it in UC-22.6.<br>3. The ticket has a status that fits the action: Chờ tiếp nhận for "Tiếp nhận xử lý" or "Từ chối"; Đang xử lý for "Hoàn tất". |  |  |
| Normal Flow | **Accept and complete a ticket**<br>1. The Shop Owner chooses "Tiếp nhận xử lý" on a ticket whose status is Chờ tiếp nhận.<br>2. The system checks that the ticket is Chờ tiếp nhận (GBR-WP-01), changes its status to Đang xử lý, records an audit entry and displays “Đã tiếp nhận xử lý yêu cầu bảo hành.”<br>3. The Shop Owner handles the ticket with the customer outside the system (contact, inspection, repair or part replacement).<br>4. When finished, the Shop Owner chooses "Hoàn tất" on the in-progress ticket, enters the "Kết quả xử lý" (required, at most 4000 characters) and confirms.<br>5. The system checks that the ticket is Đang xử lý and validates the result according to GBR-WP-03, changes the ticket status to Hoàn tất, stores the result and the completion time, records an audit entry and displays “Đã hoàn tất yêu cầu bảo hành.” The use case ends. |  |  |
| Alternative Flows | **Step 1_Reject the ticket**<br>1. For a ticket whose status is Chờ tiếp nhận, the Shop Owner chooses "Từ chối", enters the "Lý do từ chối" (required, at most 2000 characters) and confirms.<br>2. The system checks that the ticket is Chờ tiếp nhận and the reason according to GBR-WP-02, changes its status to Bị từ chối, stores the reason, records an audit entry and displays “Đã từ chối yêu cầu bảo hành.” The use case ends.<br><br>**Step 4_Not covered by the warranty**<br>1. After accepting the ticket, the Shop Owner inspects the product and finds that it is not covered by the warranty (for example damage caused by impact or outside the warranty scope).<br>2. The Shop Owner chooses "Hoàn tất" and records a result of the form "Không bảo hành vì …" (GBR-WP-03). Continue at step 5; the ticket still becomes Hoàn tất and does not become Bị từ chối.<br><br>**Step 1_Ticket is already Đang xử lý**<br>1. If the ticket was accepted earlier, the Shop Owner starts at step 4.<br><br>**Step 4_Cancel**<br>1. The Shop Owner closes the "Hoàn tất yêu cầu bảo hành" or "Từ chối yêu cầu bảo hành" dialog.<br>2. The system does not change the ticket. The use case ends. |  |  |
| Exception Flow | **Step 1_No permission**<br>1. If the user is not signed in or the session has expired, the system displays “Chưa xác thực hoặc phiên đăng nhập đã hết hạn”.<br>2. If the user is not the Shop Owner, the system rejects the request and displays “Bạn không có quyền thực hiện thao tác này”.<br>3. The use case ends.<br><br>**Step 1_Ticket not found**<br>1. If the ticket no longer exists (in step 1, step 4 or the reject flow), the system changes nothing and displays “Không tìm thấy yêu cầu bảo hành: <mã yêu cầu>”.<br>2. The user reloads the list. Return to UC-22.6.<br><br>**Step 2_Accepting in a wrong status**<br>1. If the ticket is no longer Chờ tiếp nhận (for example it was already accepted, or the customer has just cancelled it), the system does not change the status and displays “Chỉ có thể tiếp nhận xử lý yêu cầu bảo hành đang ở trạng thái Chờ tiếp nhận (NEW). Trạng thái hiện tại: <trạng thái>”.<br>2. The user reloads the list. Return to UC-22.6.<br><br>**Step 5_Completing in a wrong status**<br>1. If the ticket is not Đang xử lý (including Chờ tiếp nhận: a ticket cannot be completed before it is accepted), the system does not change the status and displays “Chỉ có thể hoàn tất yêu cầu bảo hành đang xử lý (IN_PROGRESS). Trạng thái hiện tại: <trạng thái>”.<br>2. The user reloads the list. Return to UC-22.6.<br><br>**Step 5_Invalid processing result**<br>1. If the result is empty or longer than 4000 characters, the system does not change the status and displays “Dữ liệu đầu vào không hợp lệ”; if the result is missing but the data still reaches the business step, it displays “Phải nhập kết quả xử lý khi hoàn tất yêu cầu bảo hành.”<br>2. The user enters the result again. Return to step 4.<br><br>**Step 1_Invalid rejection**<br>1. If the reason is empty or longer than 2000 characters, the system does not change the status and displays “Dữ liệu đầu vào không hợp lệ”; if the reason is missing but the data still reaches the business step, it displays “Phải nhập lý do khi từ chối yêu cầu bảo hành.”<br>2. If the ticket is no longer Chờ tiếp nhận (for example it was already accepted), the system displays “Chỉ có thể từ chối yêu cầu bảo hành đang ở trạng thái Chờ tiếp nhận (NEW). Trạng thái hiện tại: <trạng thái>”.<br>3. The user enters the reason again or reloads the list.<br><br>**Step 2_Cannot be performed**<br>1. If the system cannot perform the action because of another error, the message shown is the system's error message or “Không thể tiếp nhận xử lý yêu cầu bảo hành”, “Không thể hoàn tất yêu cầu bảo hành” or “Không thể từ chối yêu cầu bảo hành” according to the action.<br>2. The ticket keeps its status. The user tries again.<br><br>**Step 5_Recording the audit entry fails**<br>1. The audit entry is recorded after the status change has been saved successfully. If recording fails, the new status is kept and the failure is written to the system log for follow-up.<br>2. The user still sees the success message. |  |  |
| Postconditions | 1. After step 2 the ticket is Đang xử lý.<br>2. After step 5 (including the "Not covered by the warranty" flow) the ticket is Hoàn tất and has a processing result and a completion time.<br>3. After the reject flow the ticket is Bị từ chối and has a rejection reason.<br>4. Every successful status change has one audit entry containing the responsible user, the old and new status, the result or reason and the time (see "Step 5_Recording the audit entry fails").<br>5. The customer can see the status, the processing result or the rejection reason of the ticket they submitted.<br>6. When the action is not successful or is cancelled, the ticket keeps its status, result and reason; no audit entry is recorded. |  |  |

## Business Rules

| GBR-ID | Rule Statement | Applies To | Rationale | Enforced By |
| :-: | :-- | :-: | :-- | :-- |
| **GBR-WP-01** | Ticket life cycle: Chờ tiếp nhận → Đang xử lý → Hoàn tất; or Chờ tiếp nhận → Bị từ chối. Hoàn tất, Bị từ chối and Đã hủy are final statuses and cannot change further. Only a Chờ tiếp nhận ticket can be accepted for processing. Đã hủy is set only by the customer while the ticket is still Chờ tiếp nhận and is outside this use case. | UC-22.7 (step 2) | Each ticket follows a clear process and is never handled twice or skipped ahead. | System (warranty ticket service) |
| **GBR-WP-02** | Only a Chờ tiếp nhận ticket can be rejected; the rejection reason is required, at most 2000 characters. Once accepted, a ticket can no longer be rejected. | UC-22.7 ("Step 1_Reject the ticket" flow) | Rejecting makes sense only before handling starts; the reason helps the customer understand the decision. | System (warranty ticket service) |
| **GBR-WP-03** | Only a Đang xử lý ticket can be completed; the processing result is required, at most 4000 characters. A case found not eligible for the warranty during handling is still completed with a result "Không bảo hành vì …" and does not become Bị từ chối. | UC-22.7 (step 5, "Step 4_Not covered by the warranty" flow) | Every accepted ticket ends with a result so the customer gets a clear answer. | System (warranty ticket service) |

## Out of Scope (not supported by the current code or covered by another use case)

| Item | Note |
| :-- | :-- |
| Assigning technical staff, creating technical jobs | Removed from the system |
| Sending e-mail or SMS to the customer when the status changes | Not done by the system; the customer follows the status in the customer portal |
| Submitting and cancelling a ticket by the customer | Customer function |
| Viewing the ticket list and details | Covered by UC-22.6 |
