UC-23 – Record Staff-Assisted Payment Receipt

Primary ActorsSales Staff, Shop OwnerSecondary ActorsNone
Created ByPham Van NamCreated Date24/11/2026
DescriptionAs a staff member who is allowed to collect money, I want to record an amount that the customer has paid for an order (cash already received, or a bank transfer declared by the customer), so that the collected amount and the remaining balance of the order are always correct, and bank transfers are verified by an accountant afterwards.
Preconditions1. The user is logged in with the Sales Staff or Shop Owner role.
2. The order exists, is not cancelled and still has a remaining balance greater than 0.
Normal FlowRecord a payment
1. The user opens the details of the order for which a payment is to be recorded.
2. The system displays the "Thanh toán theo tiến độ" (Payment by milestone) section with the Verified amount, the Pending verification amount, the Remaining balance, the progress of the payment milestones and the history of the order's receipts.
3. The user chooses "Ghi nhận thanh toán" (Record payment).
4. The system displays the "Ghi nhận thanh toán" dialog with: the remaining balance, the payment method (Cash – verified immediately, or Bank transfer – pending verification), the amount (VND), the bank transfer reference (only for bank transfer, optional) and a note (optional).
5. The user selects the method, enters the amount (and the reference and note if any) and chooses "Tiếp tục" (Continue).
6. The system checks the amount (Recorded data: the method is Cash or Bank transfer (required); the amount is greater than 0 (at most 2 decimal places); the bank transfer reference is optional, at most 255 characters; the note is optional, at most 1000 characters) and GBR-PY-02, then displays the "Xác nhận ghi nhận" (Confirm recording) step showing the formatted amount and the method.
7. The user chooses "Xác nhận ghi nhận".
8. The system checks that the order can receive payments according to GBR-PY-01 and that the amount does not exceed the remaining balance according to GBR-PY-02.
9. The system records the receipt: for cash it records "Đã xác minh" (Verified), updates the payment status of the order and allocates the receipt to invoices according to GBR-PY-03; for a bank transfer it records "Chờ xác minh" (Pending) according to GBR-PY-04.
10. The system closes the dialog, refreshes the progress and the payment history, and displays “Đã ghi nhận <số tiền> tiền mặt (đã xác minh).” or “Đã ghi nhận <số tiền> chuyển khoản, chờ kế toán xác minh.”
Alternative FlowsStep 3_Payment cannot be recorded
1. If the order is fully paid, the "Ghi nhận thanh toán" button is disabled with the hint "Đơn đã thanh toán đủ".
2. If the order is not in a status that accepts payments, the button is disabled with the hint "Đơn không ở trạng thái nhận thanh toán". The use case ends.

Step 5_Choose bank transfer
1. The user selects the "Chuyển khoản" method.
2. The system additionally displays the "Mã tham chiếu chuyển khoản" field (optional, at most 255 characters). Continue at step 5.

Step 6_Go back to edit
1. On the "Xác nhận ghi nhận" step the user chooses "Quay lại chỉnh sửa" (Back to edit).
2. The system returns to the entry form with the entered data. Return to step 5.

Step 7_Same request submitted again
1. If the request is submitted again (several clicks, or a resend after a network error) with the same content, the system does not create another receipt.
2. The system returns the receipt already recorded and displays the message as in step 10.

Step 5_Cancel
1. The user closes the dialog without confirming.
2. The system records no receipt. The use case ends.
Exception FlowStep 1_No permission
1. If the user is not signed in or the session has expired, the system displays “Chưa xác thực hoặc phiên đăng nhập đã hết hạn”.
2. If the user is not a Sales Staff or Shop Owner (GBR-PY-05), the system does not allow recording and displays “Bạn không có quyền thực hiện thao tác này”.
3. The use case ends.

Step 2_Payment information cannot be loaded
1. If the system cannot load the payment information, it displays “Không tải được thông tin thanh toán của đơn.”
2. The user reloads the page. Return to step 1.

Step 6_Invalid amount
1. If the amount is not greater than 0, the system displays “Số tiền phải lớn hơn 0.”
2. If the amount is greater than the remaining balance, the system displays “Số tiền vượt số còn phải trả (<số tiền>).”
3. The system does not let the user continue. The user corrects the amount. Return to step 5.

Step 8_Order cannot receive payments
1. If the order cannot be found, the system records nothing and displays “Không tìm thấy đơn hàng”.
2. If the order is cancelled or its total amount is not valid (GBR-PY-01), the system records nothing and displays “Đơn hàng không thể nhận thanh toán”.
3. The use case ends.

Step 8_Amount exceeds the remaining balance
1. If another receipt was recorded while the user was entering data and the amount now exceeds the remaining balance (GBR-PY-02), the system records nothing and displays “Số tiền vượt số còn phải trả”.
2. The user reloads the information and enters the amount again. Return to step 3.

Step 8_Request code used with different data
1. If the request code has already been used for a receipt with different content, the system records nothing and displays “Mã yêu cầu đã được dùng với dữ liệu khác”.
2. The user closes the dialog and opens it again to create a new request. Return to step 3.

Step 8_Submitted data is invalid
1. If the submitted data is invalid and the screen did not block it, the system records nothing and displays “Dữ liệu đầu vào không hợp lệ”.
2. The user corrects the data. Return to step 5.
Postconditions1. After step 9 a new receipt of the order is saved with the method, amount, reference, note, the user who recorded it and the recording time.
2. For cash: the receipt is "Đã xác minh" (Verified), is added to the paid amount immediately and the payment status of the order is updated.
3. For a bank transfer: the receipt is "Chờ xác minh" (Pending) and is not added to the paid amount until an accountant verifies it.
4. When the action is not successful or is cancelled, no receipt is saved and the payment status of the order does not change.

Business Rules

GBR-PY-01A payment can be recorded only for an order that exists, is not Cancelled and has a total amount greater than 0.UC-23 (step 3, step 8)Do not collect money for an order that is no longer valid.Screen (button disabled) and the system (order check)
GBR-PY-02The recorded amount cannot exceed the remaining balance of the order. Remaining balance = order total − the sum of verified receipts − pending cash-on-delivery (COD) receipts.UC-23 (step 6, step 8)Do not collect more than the order's obligation and avoid overlapping with a pending COD receipt.Screen (checked first) and the system (final check)
GBR-PY-03Cash actually received by the staff member is recorded as "Đã xác minh" (Verified) immediately: the receipt is added to the paid amount, the order's payment status becomes Fully paid when the paid amount equals the order total (otherwise Partially paid), and the system automatically allocates the receipt to the customer's eligible electronic invoices, oldest invoice first.UC-23 (step 9)Cash has really been received, so it is reflected in the order and the customer's debt immediately.System (payment service, order status update, payment allocation)
GBR-PY-04A bank transfer declared by the customer is recorded as "Chờ xác minh" (Pending); it is not counted in the paid amount and does not change the payment status of the order until an accountant verifies or rejects it in the bank transfer verification use case.UC-23 (step 9)The system cannot check the bank automatically, so an authorized person must confirm the money has arrived.System (payment service)
GBR-PY-05Only Sales Staff and Shop Owner can record payments; an Accountant can only view the history, summary and milestone progress.UC-23 (step 1)Separate receiving money from verifying money to control fraud.System (role check) and screen (button hidden for users without permission)
